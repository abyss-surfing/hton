# Журнал решений «Хтонь»

Хронологический лог всех договорённостей по проекту `~/code/hton`.
Каждый пункт — прямое требование или факт из диалога.

## Контекст сервера (как есть сейчас)

1. VPS VPS provider (region), Ubuntu 26.04.1, IP 203.0.113.10 — выделенный, на eth0/24, постоянный.
2. Занятые порты: 443 tcp+udp — `amnezia-xray` (docker, от редиректит на google.com);
   8443 — `outline-operator-two`; 4431 — `amnezia-telemt` (mtproto, тот самый «telemet»);
   33033/33034 udp — AmneziaWG; 80 — Apache (дефолт-страница, /var/www/html).
3. На сервере второй пользователь `operator-two` (Outline и часть Amnezia — его) — координация любоо воздействия.
4. IPv6 нет; план — HE-туннель (connecлятиться заново, PoP region), AAAA на домен.

## Почему текущий MTProto «иногда» работает

- ТСПУ работает вероятностно: при неуверенности дропает часть пакетов → «проходит через раз».
- fakeTLS имитирует TLS только в ClientHello; фрейминг дальше — MTProto → эвристики DPI.
- У telemt три сигнала: порт 4431 (нестандартный), самоподписанный серт, за портом нет сайта.
- Лечение: перенос за haproxy на 443 + настоящий серт + настоящая сайт-маска.

## Протоколы: что берём / что нет

- **VLESS+Reality / WS/XHTTP** — ядро (xray).
- **NaïveProxy** — «концепция нравится, ставь»; маскировка — Chrome-стек на КЛИЕНТЕ,
  сервер — caddy+forwardproxy; CONNECT-метод как路由-критерий в haproxy.
- **QUIC/Hysteria2** — «провайдеры разные бывают» — оставить; UDP-порт, автоподбор, вне haproxy.
- **IPsec** — отклонён: ISAKMP (udp 500/4500) — старая известная сигнатура, палит IP, риск для всей машины.
- **SOCKS5** — никогда не публичен (хендшек читается, повод для бана IP); только внутри:
  локальный socks VLESS-клиента, либо SSH `-L` к socks-internal (127.0.0.1:10002, user/pass).
- **SS/Outline** — голый SS детектится; он и так на своём порту, под 443 TLS без пере-wrapping не спрятать.

## Имена и бренд

- Проект: **hton** (вариант «хтонь»); смыслы: хтонь, https, тоннель, ton/tg; пиво для C-famnier htonl.
- Командный стиль: `hton <cmd>`; README-легенда: «Настоящий сайт наверху. Хтонь — внизу».

## Порты и переключение

- Главный публичный порт: переменная `PUBLIC_PORT` в .env; дефолт 4443 (443 занят), остальные кандидаты в PORT_CANDIDATES.
- `scripts/switch` меняет 4443↔443 и правит .env; перед 443 — валидация занятости.
- UDP-порт hysteria: автоподбор из списка.
- Порт 80 не трогаем: Apache остаётся; серты идут dns-01 (http-01/80 не нужны), но фрост «использование 80 не проблема» — редирект http→https можно добавить позже.

## Сертификаты

- Провайдер домена: **internetbs.net**; acme.sh поддерживает нативно (dns_internetbs, API key/password из панели).
- Все серты через acme.sh dns-01: уникальные домены И wildcard (`*.домен`).
- Нет certbot; haproxy-native ACME не ставим ставку (молодой); единый путь — acme.sh.
- Hook: пересборка crt-list + graceful reload haproxy.

## Docker-архитектура

- «Постарайся всё упаковывать в докеры»: haproxy, xray, caddy(+naive), unbound, mtg, admin, hysteria — контейнеры; образы alpine-base, пинуются по digest.
- Отдельный контейнер на haproxy и отдельный на DNS (unbound) — явно.
- Сеть: bridge (`vpn-net`); passthrough к чужим стекам через host-gateway.
- HAProxy — «край», единственный держатель TLS (пользователь подтвердил: haproxy быстрее на входе; nginx/caddy/traefik — вторым слоем при нужде; traefik отклонён, caddy выбран как сайт-маска).
- Docker при отсутствии: ubuntu → apt по официальной инструкции Docker (repo docker-ce); прочие ОС → инструкция+ссылки, подтверждение, re-check.
- Внутри контейнеров — alpine.

## CLI-контракт (hton)

- `bin/hton` — тонкий диспетчер, тупо зовёт `scripts/*`; реальные скрипты в `scripts/`.
- Общий код — `lib/` (без .sh-суффикса), DRY/SOLID/KISS.
- `lib/hton` содержит: env-хелперы, порты, журнал, docker-check, ask-menu.
- `install` спрашивает путь в PATH — по умолчанию НЕТ.
- systemd: `sudo service hton start/stop/restart`, автозагрузка автоматически.
- Командный список: install, update, diag, restart, keys, share, switch, remap-undo, tunnel, backup.
- diag нужен в первую очередь пользователю (самопроверки).

## Меню установки (.env-driven)

- Всё системное описывается INSTALL_* переменными в .env: `scripts/install` ЯВНО спрашивает ставить ли каждый пункт.
- Скорое правило: ключа нет в .env → ответ по умолчанию «нет»; «да» = да.
- Изменённый ответ прописывается обратно в .env — на повторном запуске не переспрашивается.
- Цели INSTALL_*=vless/dns/admin/site/systemd/naive/hysteria/mtproto-выбор — полный список.

## Fresh-server сценарий (install через клиентов)

- Amnezia — нельзя headless; itinerary: чек-лист «наличие на клиенте» + wait-цикл до появления контейнеров; потом ремап.
- Hysteria2 — авто (script) + hysteria2://-ссылка.
- Outline — официальный install script печатает onboarding-URL; вставка в Outline Manager = «с админским доступом».

## Адаптеры и откаты

- Каждое изменение чужого контейнера журналируется: что меняли, как, как откатить (полная исходная конфигурация/команда).
- Compose-стеки: правим рабочий файл, храним `docker-compose.orig.<proj>.yml`.
- Outline: «пока отключить и убрать из автозагрузки» — stop + restart=no (не удалять).
- Reinstall Amnezia заново захватит 443 → `hton update` повторно ремапит (записать в доки).

## Admin / киллер-фичи

- Свой вэб-фронт: простой, минималистичный, vanilla.
- Секретный URL: `https://домен/xxxxxxxxx` → админка; всё остальное — обычный сайт.
- Shell: haproxy остаётся входом (быстрее на входе); caddy вторым слоем — маска-сайт.
- TG-бот как админка: long-polling (не webhook), whitelist ADMIN_TG_IDS; doctor-уведомления в чат.
- Revoke холодный (restart xray) — ок; перезагрузка не критична.
- docker.sock только у admin-контейнера, whitelist действий (restart xray/haproxy).
- Rust для бэкенда: «нравится» — axum + reqwest, scratch-контейнер, multi-stage сборка.
- Киллер-фичи (предлагавшиеся): doctor/самолечение, бэкап секретов (age), метрики по ТГ,
  multi-user шаринг+квоты (v2), усиленная сайт-маска.

### Д24. Архитектура кода: bash-first (ОТМЕНА «всё на Rust» — словами пользователя)
> «я не понял прикола удалить scripts/* — наоборот старайся всё написать на баш-скриптах!
> на простых юникс-вей командах. bin/hton нужен чтобы запускать команды откуда угодно
> (из любой папки). и его тоже можно оставить на голом баше. а вот сложную логику
> которая займёт слишком много места на баше или будет слишком сложно тестируемой
> можно написать на нормальном яп».

Следствия:
- scripts/* НЕ удаляются никогда — это основной стиль; bin/hton — тонкий bash-диспетчер
  (запуск команд из любой папки), тоже голый bash;
- приоритет: простые unix-вей команды на bash; единственное исключение —
  сложная/трудно-тестируемая логика → нормальный ЯП (Rust: admin-сервер и части
  команд при необходимости);
- обновить: README (EN), ARCHITECTURE (§Lang/CLI/структура), sdd-cli (переписать:
  bash-first, Rust — исключение), sdd-whoami (whoami остаётся bash-командой),
  sdd-installer (меню-движок на bash), t02 (без удаления scripts/*).

### Д25. Автопилот на голой ОС (нормативно)
- «этот проект — должн быть первое что я захочу установить на новом ввпс купленном
  следующий раз — я выберу убунту. надо чтобы всё работало на автопилоте на голой ос».
- Следствия: `bin/hton install` позиционируется ПЕРВОЙ командой на чистой Ubuntu:
  голая ос (даже docker отсутствует) → bootstraper ставит нужные пакеты сам
  (apt → docker официальный репо → age/qrencode/etc), затем меню INSTALL_* → полный
  подьми. Никаких пред.Install-ручных шагов не предполагается. Отразить: sdd-installer
  (INS-0), README quickstart, ARCHITECTURE §install.

### Д26. Локальная сеть и роутер (нормативно от пользователя)
> «подумай как сделать так чтобы я мог на обычном дешёвом роутере что-то сделать
> и заработал VPN через эту хтонь».

Вывод мышления (фиксирую как рамку требований):
- Серверная часть (hton) меняется МИНИМАЛЬНО: наш vless(xray, WS/XHTTP за хапрокси
  на 443) + DoT(853) уже пригодны для «роутерного» сценария — нужен только клиент
  на роутере.
- «Обычный дешёвый роутер» на стоковой прошивке клиента запустить не может:
  значения имеет лишь открытость прошивки (OpenWrt) или вендорский VPN-клиент.
- Реалистичные сценарии:
  A) Сток-прошивка — VPN на конечных устройствах (без роутера); уже работает.
  B) OpenWrt/минироутер (GL.iNet из коробки — дёшево, микросхемный OpenWrt):
     xray-core на роутере (luci-app-passwall2 / nikki) → весь LAN за роутером
     ходит через hton без клиентских приложений; DNS вверх — наш DoT 853;
     разделённая маршрутизация (только заблокированное/или всё).
  C) Вендорские VPN-клиенты стока (Keenetic WG/L2TP и т.п.) — НЕ годятся:
     раннее решение про IPsec/WG остаётся (DPI ТСПУ), не используем.
- Удобство сервера: выдавать готовые конфиги для роутера командой share
  (см. контракт §16: `share --router`).

### Д27. SSH-туннель как роутерный путь (нормативно от пользователя)
> «а если ssh-туннель?» — принято в Д26 как вариант D (рядом с vless-рецептом):
- **D1 («-D»)**: `ssh -D 1080` (autossh-ревив) с роутера →urger passwall2-noda
  «socks → 127.0.0.1:1080» → весь LAN. НА СЕРВЕРЕ НИЧЕГО не нужно (только
  sshd + ключ на роутере — они уже есть: он же ходит в VPS по ssh).
- **D2 («-w»)**: `ssh -w 0:0` полноценный L3-туннель (kmod-tun на OpenWrt):
  на сервере нужен спец-юзер `tunneluser` (PermitTunnel, forced command,
  ограничение keys), sshd PermitTunnel, ip_forward+MASQUERADE для его подсети
  — добавляется минимально (journal: шаги в состав install как INSTALL_SSH_TUNNEL,
  дефолт нет; бэкапом/remap-в-устав stance не меняет чужие стеки).
- Ограничение честно передано владельцу: SSH — известный DP-фингерпринт,
  ТСПУ периодически душит/blokite SSH; поэтому vless остаётся ОСНОВНЫМ,
  SSH — запасной/самый простой (ничего лишнего на роутере: openssh-client +
  autossh, без xray/gen_passwall).
- Выдача конфига: `share --router --ssh` (см. contract §16).

### Д28. SSH-туннель — только в рамках сессии (уточнение Д27, нормативно)
> «желательно только в рамках сессии: как только я закрою ssh — туннель тоже
> пропадёт, иначе если он сломается будет проблема».

Следствия (RTR-9):
1. НИКАКОГО autossh/ревайва: туннель живёт пока жива ssh-сессия; закрыл ssh
   (или сессия умерла) → туннель исчез.
2. Сломался ssh → туннель должен пропасть СРАЗУ иگرد не крутить вечное
   переподключение (никаких зомби-состояний и «висит полумёртвый туннель»);
   ClientAliveInterval/ExitOnForwardFailure, TCPKeepAlive — чтобы обрыв был
   обнаружен быстро.
3. Роутер в этот момент НЕ чёрная дыра: маршрут через туннель conditional —
   туннеля нет → интернет напрямую (fallback прямой, без правил-хвостов).
4. D2 (`ssh -w`) то же: интерфейс появляется/исчезает вместе с сессией; при
   отсутствии tun0 на роутере дефолт-маршрут прямой (metric fallback).

### Д29. Комбайн и декларативные фичи (2026-10-31)

Прямые запросы владельца:
> «давай всё добавим в планы. нужна конфетка-комбайн».
> «нужен максимально удобный фича-тогл через конфиг. возможно не .env ...
> вэб админку переключалку генерилку ключей ... базовое неотключаемое-core,
> а контейнеры с впн подключаемые на уровне декларативного конфига и
> самонастраиваемое через scripts/install. всё пропиши в архитектуре и планах».

Фиксируем требования: модульный план, базовое ядро, декларативные VPN-компоненты,
веб-переключатели/ключи и самонастройка install. Выбор hton.yaml, схема secretRef,
ревизии и границы approved envelopes — инженерный дизайн, а не цитаты владельца.
Эта редакция заменяет .env как главный конфиг и прежнее read-only ограничение
веба для модулей. Слабый VPS, bash-first, внешняя сборка, восстановление и явные
стоп-точки сохранены. IPsec/публичный WG не включены автоматически; Tailscale
планируется с явным ограничением внедрения. Контракты: ../specs/sdd-config.md,
../specs/sdd-capabilities.md, ../CLI.md; этапы T14–T26 в ../ROADMAP.md.

### Д30. Личные кабинеты и одноразовая выдача — после релиза

Требования владельца: единый интерфейс выдачи с выбором протоколов; значения
по умолчанию из конфига (сейчас Amnezia); логин → протоколы → именованные токены.
Имя по умолчанию — дата, затем редактируется. Секреты показываются только при
создании, после закрытия повторного показа нет: удалить/отозвать и создать новый.
Свой ЛК у каждого; админ видит всех, но правило одноразового показа не обходит.
Владелец явно отложил реализацию до ПОСЛЕ РЕЛИЗА. Детали: ../specs/sdd-identity.md,
план F01–F05. Дефолт Amnezia не означает автоматическое включение нового протокола.

### Д31. Публикация локального сайта на домене проекта

Запрошен reverse proxy/проброс для локального сайта на финальном домене проекта.
План: private upstream либо исходящий reverse tunnel через NAT, HTTPS в Caddy,
домен/поддомен/совместимый путь, защищённые маршруты core. Инженерное размещение
в отложенной фазе — F06–F08, ../specs/sdd-web-publish.md; backend туннеля ещё
подлежит квалификации. Реального проброса/публикации пока не выполняем.
