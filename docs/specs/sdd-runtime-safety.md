# SDD runtime safety — VPN survives management failure

> Authority: [owner requirements](../OWNER-REQUIREMENTS.md). R1 is standalone CLI/Core with manual YAML validation and safe apply; API/configurator/web implementation is deferred. Native checks are required, Docker staging optional, IPv6 far future. See [final audit](../FINAL-REVIEW.md) for unresolved design details.

## Authority and invariant

Owner requirement, 2026-10-31: custom admin/configuration/automation failures must
not break VPN/HAProxy routing or the ordinary site; optional Docker staging can test complex changes. Retain a verified working version. This governs all other design documents.

Separate the DATA PLANE (HAProxy, Caddy and selected VPN/DNS/tunnel engines) from
the CONTROL PLANE (admin, config compiler, optional agents, UI, telemetry). No
request-time authentication, DNS, routing or backend config may depend on the web
admin, controller, its database, compiler or schema service being up. Use native
backend credential/config mechanisms. Booting accepted VPN config does not run the
compiler, migrations, network downloads, probes that rewrite config or web login.

Core CLI/configuration mechanisms are included in installation; web administration is an optional later module. Neither VPN nor the ordinary site depends on web health. Caddy and the selected Naive
plugin are real data-plane dependencies; calling them management would be wrong.
A failed optional protocol must not stop unrelated protocols or the default site.

## Execution and ownership

Use separate Compose services/units for data plane and management. Never put
admin/controller/database under data-plane depends_on or a shared failure/restart
chain. The data-plane unit calls a minimal runtime start helper with the recorded
last-known-good bundle; it does not call hton update/install or a Rust compiler.
Management resource limits leave headroom for the VPN; its OOM/restart must not
trigger a data-plane restart. Do not give UI containers docker.sock or arbitrary
network/host privileges. All writes still require bounded controller operations.

A small runtime executor/guardian is the trusted mutation boundary, separate from
the public admin and config compiler. It accepts only prepared immutable bundle
IDs and fixed actions for owned resources, not shell, arbitrary paths or generic
Docker calls. Revalidate bundle/plan fingerprints, approvals, port ownership,
policy fences and check attestations before action. A candidate generated by a
broken compiler is untrusted until independently checked.

Service restart is admitted against the current accepted bundle and exact run epoch.
Core sends a nonempty catalogue service set from registered enabled optional/data
services; the Runtime rejects empty, Associated, missing or incompatible targets,
active trial/maintenance leases and launch drift. Each native restart is receipt-bound
under the effect lock, which also serializes trial lease admission. Post-action Running/launch checks precede declared semantic
probes for the selected service set, not unrelated accepted members. Unknown or
unsupported probes leave the journal terminal Partial with action receipts and
survivor IDs; they are never converted into a health pass.

## Accepted bundles and paths

work/bundles/<id>/ contains the protected immutable manifest, generated
Compose/configs, exact image digests, scoped secret-version references, schema/
module versions, deployment intent and validation results. Persist artifact hashes;
never rebuild/download dependencies to recreate a verified deployment at boot.
Keep required images cached; deleted images/disk failure are explicit recovery cases.

work/runtime/state.json records active, lastKnownGood and previousGood bundle IDs,
transaction/lease state and current policy fence. Active during trial is not yet
lastKnownGood. After verified commit, lastKnownGood becomes candidate and
previousGood retains the earlier compatible accepted bundle. Retention never
removes active, accepted or reserved fallback material before a new fallback exists.

Mount stable SERVICE-SCOPED runtime trees, not the whole configuration/secret
store and not individual files replaced with rename. Bundles reference immutable
per-service versions in those trees. Atomic service current references plus tested
native reload deliver config/cert changes; recreate only when image/mount/published
binding semantics require it. Track the exact effective bundle after recovery;
a pointer switch alone cannot apply data to a running process.

## Candidate admission and Docker test runner

1. Normalize desired config and render candidates away from active runtime paths.
2. Inspect generated Compose, listener/route ownership, image pins, mount/capability
   allowlists, secrets redaction and dependency graph independently of the compiler.
3. Run each selected engine's compatible pinned native validator (native tool or explicit container invocation). Dry-run
   never pulls images or starts validators that need mutation; missing tools are
   explicitly unverified. Full validation/test is a separate mutating command.
4. When optional Docker staging is selected, start the FINAL RENDERED bundle in an isolated Docker test project/network,
   overriding only host-port/network allocation through a documented deterministic
   mapping. Never reuse production credentials for uncontrolled external probes,
   mount foreign configs or publish test listeners publicly. Record test overrides.
5. For staging and protocol qualification, use real pinned clients for TLS/SNI default site, VLESS/Naive, selected raw
   passthrough and UDP cases. Match observed backend identity/candidate version;
   tests must not accidentally hit the still-running old generation. Test denied
   routes, auth and core management-path preservation. No implicit success from
   docker compose config, listening sockets or curl alone.
6. Record an attestation bound to artifact/image/secret hashes and test mapping.
   Staging cannot prove production port availability, ISP/DPI or real device support;
   those are separate preflight/external acceptance checks.

Reusable fixtures/test clients replace hand-written protocol implementations.
Tests run outside the weak VPS where possible; on-host staging is bounded and
scheduled explicitly. Full Docker tests may mutate their isolated test resources,
so never label them dry-run or run them on every web toggle click without a budget.

## Guarded promotion and independent recovery

First installation has no prior accepted VPN: use an explicit pre-install/closed-listener rollback target, preserve foreign resources and local SSH recovery, then record the first verified bundle. Never invent a previous-good ID.

Persist intent and reserve a compatible fallback before changing active services.
Start an independent runtime guardian before activation; if verification/commit
lease expires or the management process dies, it compensates the in-flight change.
The guardian uses a durable lease and accepted bundles, not the failed web process.
After activation, independently verify required routes/credential policy and only
then commit. Refuse promotion when no tested rollback route exists.

Use native graceful reload when supported; long VPN sessions and workers may
remain pinned to old config. Observe retirement, never prune their files early.
Changes requiring recreation/port takeover can disconnect sessions and cannot
promise zero downtime. Release a target port before restoring its prior holder.
If compensation fails, retain evidence, mark recovery-required and protect working
unaffected routes. A temporary Internet outage is not a reason for steady-state
watchdog to endlessly restart every service or rewrite accepted config.

## Credential/policy fences

Rollback must not resurrect revoked credentials or downgrade strict IPv6-only
policy. Bundle compatibility includes current irreversible credential/policy fence,
not just prior successful health. Revocation and, in far future, egress changes prepare and validate
policy-clean active AND fallback bundles before successful confirmation, then
persist the monotonic fence. Older bundles are no longer admissible as fallback.
If no compatible safe fallback exists, isolate the affected inbound and require
recovery rather than activate known-revoked keys. Other protocols remain up.
Certificate rollback similarly checks current validity; retain usable renewed
material instead of restoring an expired certificate blindly.

An explicit `runtime.rollback` may select only the `previousCompatible` target in
the current committed lease. Runtime independently rechecks its protected manifest,
exact resource bindings, certificate expiry and monotonic credential fences before
inverse native effects and immediately before terminal acceptance. This action is
distinct from guardian recovery of an uncommitted trial. It runs only while the
current epoch remains Running; a later StopIntent fences restart and accepted-state
promotion.

## Failure tests and limits

Kill admin/controller/compiler, corrupt their desired config or metadata, exhaust
management's memory limit, interrupt each apply transition and reboot with those
components unavailable. Existing VPN and cold boot from last-known-good must work.
Test invalid final configs, stale attestations, missing image/secret files, broken
candidate auth/route, lease expiry, failed rollback and revoked-key fences. Keep a
minimal local CLI recovery path independent of admin/frontend.

This protects against expected software failures and rejected changes. It cannot
guarantee availability after root compromise, kernel/Docker failure, lost disk,
expired external credentials, provider outage or a bug in a selected data-plane
engine. Report boundaries; do not claim an impossible absolute guarantee.

## Lock ownership and hung management

Config lock serializes desired edits/planning; runtime lock serializes short native
effects. Do not hold a management-owned config lock while waiting for an activation
trial. Runtime lease/state fences block competing promotions; the independent guardian
owns compensation authority after lease expiry. A hung control process must not
indefinitely hold a lock needed for rollback. Bound native action timeouts and test
both killed and alive-but-stalled management. Avoid nested cross-process lock waits.

## Run intent overrides recovery

See [lifecycle](sdd-lifecycle.md). Persist stopped intent under `work/runtime/`
before down effects; accepted boot, trial rollback, renewal and watchers must
check that intent. A guardian may preserve/restore artifacts after a later down,
but cannot restart services. Down uses the durable associated-resource registry
even with malformed desired YAML. Disable systemd and Docker/external restart
owners; partial stop reports remaining resources and keeps the boot prohibition.
Ordinary manual up validates desired YAML and refuses automatic substitution;
explicit accepted-bundle startup is separate. Automated permitted cold boot uses
accepted artifacts without parsing desired YAML.

Native check evidence is required; optional Docker-staging attestation is bound
to the candidate only when requested. Lack of optional staging is not an admission
error. Real-client release qualification remains distinct. Replace old `var/*`
runtime paths with `work/*` per architecture; secrets live in `config/secrets/`.

## I3 host observation binding

Independent hton-host supplies private bounded Linux process mechanics and fixed
read-only Docker/systemd inspection. Protected native launch facts are inputs to
future admission/identity observers, not evidence of ownership or semantic health.
Its API cannot pull/start/update or run shell/config-selected commands. See
INTERFACES “I3 bounded native observation transport”. D81 defers intermediate
compilation until all selected implementation plans are complete; product runtime
validation remains required behavior and final U0/F0 order is unchanged.
